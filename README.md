# Пет-проект: Сервис межбанковских переводов по номеру телефона внутри банка

Репозиторий содержит архитектурное описание, системные требования и структуру базы данных для критически важного банковского сервиса мгновенных переводов. Проект спроектирован с учетом требований к высокой отказоустойчивости (Fault Tolerance) и производительности.

---

## Раздел 1. Бизнес-контекст и User Story

*   **Цель проекта:** Создать надежный и быстрый сервис, позволяющий клиентам банка переводить денежные средства по номеру телефона без необходимости ручного ввода полных реквизитов карт или счетов.
*   **User Story:** Как пользователь, я хочу переводить деньги по номеру телефона клиентам банка, чтобы быстро и удобно отправлять средства без ввода полных реквизитов карты.

---

## Раздел 2. Системные требования

### 2.1. Функциональные требования (ФТ)
*   **ФТ-1 [Валидация номера]:** Поле ввода номера телефона получателя является обязательным. Маска ввода должна строго соответствовать форматам: `+7 (XXX) XXX-XX-XX` или `+7XX (XXX) XXX-XX-XX`.
*   **ФТ-2 [Проверка участников]:** Отправитель и Получатель перевода должны быть действующими клиентами банка (активные записи в таблице `users`).
*   **ФТ-3 [Проверка статуса счетов]:** Перевод возможен только в случае, если счета Отправителя и Получателя имеют статус `ACTIVE` (не заблокированы, отсутствуют аресты и ограничения).
*   **ФТ-4 [Ограничения по сумме]:** Сумма разового перевода должна быть строго больше 0 рублей и не может быть отрицательной. Минимальный порог интерфейсной валидации — 100 рублей.
*   **ФТ-5 [Конвертация валют]:** Система должна поддерживать автоматическую конвертацию средств в реальном времени по внутреннему курсу банка, если валюта счета Отправителя отличается от валюты счета Получателя.
*   **ФТ-6 [Интерфейс конвертации]:** При несовпадении валют система обязана до подтверждения транзакции отобразить пользователю:
    1. Текущий курс конвертации банка.
    2. Итоговую сумму списания в валюте Отправителя.
    3. Итоговую сумму зачисления в валюте Получателя с корректным графическим символом ($, €, ₽).

### 2.2. Требования к отказоустойчивости и автономности (Fault Tolerance)
*   **FT-1 [Обработка потери сети]:** Мобильное приложение должно аппаратно определять отсутствие интернет-соединения. При потере связи кнопка «Перевести» блокируется, операция прерывается с выводом алерта: *«Отсутствует подключение к интернету. Проверьте настройки сети»*.
*   **FT-2 [Локальное кеширование]:** При разрыве соединения введенные данные формы (номер, сумма, счет) сохраняются локально в зашифрованном виде. При восстановлении сети форма заполняется автоматически.
*   **FT-3 [Время жизни кэша (TTL)]:** Локальный кэш формы уничтожается аппаратно в следующих случаях:
    * При успешном завершении транзакции.
    * Принудительно при логауте пользователя (`Выйти из аккаунта`).
    * По тайм-ауту через 20 минут неактивности пользователя.

### 2.3. Нефункциональные требования (НФТ)
*   **НФТ-1 [Производительность бэкенда]:** Время обработки (Latency) операции перевода на стороне бэкенда не должно превышать **50 мс (0.05 сек)** при нормальной нагрузке (95-й перцентиль).
*   **НФТ-2 [Бизнес-лимиты]:** На уровне ядра системы зафиксированы лимиты для физлиц:
    * Максимальная сумма одной транзакции: 60 000 рублей.
    * Максимальный совокупный объем переводов в календарный месяц: 500 000 рублей.
*   **НФТ-3 [Кроссплатформенность]:** Стабильная работа клиентской части на ОС: iOS (13.0+), Android (8.0+), HarmonyOS, а также отечественных мобильных ОС (Аврора, Роса Мобайл, РЕД ОС М, KvadraOS).

## Раздел 3. Сценарии использования (Use Cases)

### UC-1: Перевод денежных средств по номеру телефона
*   **Актёр:** Авторизованный клиент (Отправитель).

#### Основной успешный сценарий:
1. Отправитель выбирает счет списания, вводит номер телефона Получателя и сумму, затем нажимает «Перевести».
2. Система валидирует корректность суммы (ФТ-4).
3. Система выполняет поиск Получателя по номеру телефона в БД.
4. Система проверяет статусы счетов (ФТ-3) и доступные лимиты Отправителя (НФТ-2). Денег достаточно.
5. Система производит списание и зачисление средств в рамках **единой атомарной транзакции базы данных**.
6. Операция логируется в историю с флагом `COMPLETED`.
7. Отправителю отображается экран «Перевод успешно выполнен».

#### Альтернативные сценарии (Обработка ошибок):
*   **Сценарий А (Получатель не найден):** Система прерывает процесс, пишет лог `FAILED` с кодом `USER_NOT_FOUND`. Пользователь видит: *«Пользователь с таким номером телефона не найден»*.
*   **Сценарий Б (Недостаточно средств):** Система прерывает процесс, транзакция пишется как `FAILED` с кодом `INSUFFICIENT_FUNDS`. Пользователь видит: *«Недостаточно средств для совершения перевода»*.
*   **Сценарий В (Превышен лимит):** Операция блокируется на этапе проверки лимитов, статус `FAILED`, код `LIMIT_EXCEEDED`. Пользователь видит: *«Превышен лимит на проведение операции»*.

## Раздел 4. Реляционная структура базы данных (PostgreSQL / Pangolin)

### 4.1. Таблица `users` (Персональные данные)
```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    phone_number VARCHAR(12) UNIQUE NOT NULL, -- Формат +7XXXXXXXXXX
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL
);
```

### 4.2. Таблица `accounts` (Счета и балансы)
```sql
CREATE TABLE accounts (
    id SERIAL PRIMARY KEY,
    user_id INT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    account_number VARCHAR(20) UNIQUE NOT NULL,
    balance DECIMAL(15, 2) NOT NULL DEFAULT 0.00, -- Защита от ошибок округления
    currency VARCHAR(3) NOT NULL,                 -- Код валюты (RUB, USD etc)
    status VARCHAR(20) NOT NULL DEFAULT 'ACTIVE'  -- ACTIVE, BLOCKED, FROZEN
);
```

### 4.3. Таблица `transactions` (Аудит и логирование операций)
```sql
CREATE TABLE transactions (
    id SERIAL PRIMARY KEY,
    sender_account_id INT NOT NULL REFERENCES accounts(id),
    recipient_account_id INT NOT NULL REFERENCES accounts(id),
    amount DECIMAL(15, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,                  -- PENDING, COMPLETED, FAILED
    error_code VARCHAR(50) NULL,                  -- Заполняется при FAILED (анализ надежности)
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```
