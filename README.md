# phone-payments-analytics
Системный анализ и проектирование сервиса внутренних переводов по номеру телефона
# Пет-проект: Сервис межбанковских переводов по номеру телефона внутри банка

Репозиторий содержит архитектурное описание, системные требования и структуру базы данных для критически важного банковского сервиса мгновенных переводов. Проект спроектирован с учетом требований к высокой отказоустойчивости и производительности.

Раздел 1. Требования
Цель: создать сервис, который позволит клиентам переводить денежные средства по номеру телефона.
User story: Как пользователь я хочу переводить деньги по номеру телефона клиентам банка, чтобы быстро и удобно отправлять средства без ввода полных реквизитов карты.

Раздел 2. Требования

2.1. Функциональные требования: 
* ФТ-1: Валидация номера телефона. Поле ввода номера телефона получателя является обязательным. Номер должен соответствовать маске: +X (XXX) XXX-XX-XX или +XX (XXX) XXX-XX-XX.
* ФТ-2: Проверка участников перевода. Отправитель и Получатель перевода должны быть действующими клиентами банка (записи о них должны существовать в базе данных).
* ФТ-3: Проверка статуса счетов. Перевод возможен только в случае, если счета Отправителя и Получателя активны (не заблокированы и на них не наложены ограничения).
* ФТ-4: Ограничения по сумме перевода. Сумма разового перевода должна быть строго больше 100 рублей. Сумма разового перевода не может быть отрицательной или равной нулю.
* ФТ-5: Конвертация валют. Система должна поддерживать автоматическую конвертацию средств в реальном времени по курсу банка, если валюта счета Отправителя отличается от валюты счета Получателя.
* ФТ-6: Отображение суммы в валюте Получателя. Если валюта счета Отправителя отличается от валюты счета Получателя, система должна до подтверждения перевода отобразить в интерфейсе:
  - Текущий курс конвертации банка.
  - Итоговую сумму списания в валюте Отправителя.
  - Итоговую сумму зачисления в валюте Получателя с указанием правильного символа валюты (например, $, €, ₽).

2.2. Требования к отказоустойчивости и автономности (Fault Tolerance):
* ФТ-1: При отсутствии интернет-соединения система должна заблокировать кнопку "Перевести", прервать операцию и вывести пользователю системное уведомление: "Отсутствует подключение к интернету. Проверьте настройки сети".
* ФТ-2: Кеширование данных формы при потере связи. При потере интернет-соединения мобильное приложение должно локально сохранять введенные пользователем данные (номер телефона получателя, сумму, выбранный счет списания). При восстановлении сети данные должны автоматически восстанавливаться в форме перевода без необходимости повторного ввода.
* ФТ-3: Безопасность и время жизни локального кэша. Локальные данные, временно сохраняемые в памяти устройства при отсутствии сети, должны быть зашифрованы. Данные должны автоматически удаляться из памяти устройства в следующих случаях:
  - При успешном завершении операции перевода.
  - По истечении 20 минут с момента последнего действия пользователя.
  - Принудительно при нажатии пользователем кнопки "Выйти из аккаунта".

2.3. Нефункциональные требования:
1. Надежность и производительность
* НФТ-1: Время отклика. Время обработки операции перевода на стороне бэкенда (с момента получения запроса до отправки ответа в мобильное приложение) не должно превышать 0.05 секунды (50 миллисекунд) при нормальной нагрузке.
2. Требования к окружению и платформам
* НФТ-2: Кроссплатформенность приложения. Клиентская часть сервиса (интерфейс перевода) должна стабильно работать на следующих операционных системах мобильных устройств:
  - Международные ОС: iOS (версии 13.0 и выше), Android (версии 8.0 и выше), HarmonyOS.
  - Российские мобильные ОС: Аврора, Роса Мобайл, РЕД ОС М, KvadraOS.
3. Бизнес-ограничения и безопасность
* НФТ-3: Лимиты на проведение операций. На уровне системы должны быть зафиксированы следующие лимиты для физических лиц:
  - Максимальная сумма одной транзакции: 60 000 рублей.
  - Максимальный совокупный объем переводов в календарный месяц: 500 000 рублей.
* НФТ-4: Мобильное приложение должно корректно определять отсутствие интернет-соединения на устройстве пользователя.
* НФТ-5: Безопасность и время жизни локального кэша (см. подробные условия очистки в пункте FT-3).

Раздел 3. Сценарии использования (Use Cases)
Наименование: Перевод денежных средств по номеру телефона внутри банка.
Актёр: Авторизованный клиент банка (Отправитель).

Основной успешный сценарий:
1. Отправитель выбирает счет списания, вводит номер телефона Получателя и сумму перевода, после чего нажимает кнопку "Перевести".
2. Система проверяет выполнение требований (ФТ-4).
3. Система выполняет поиск Получателя в базе данных банка по указанному номеру телефона.
4. Система проверяет баланс счета Отправителя и доступные лимиты (НФТ-3). Денег достаточно, лимиты не превышены.
5. Система списывает сумму перевода со счета Отправителя и зачисляет её на счет Получателя в рамках одной транзакции базы данных.
6. Система регистрирует успешную операцию в истории переводов.
7. Отправитель видит экран "Перевод успешно выполнен".

Альтернативные сценарии (Обработка ошибок):
* Сценарий 1: Получатель не найден в базе данных.
  - Система прерывает операцию, логирует статус FAILED с кодом USER_NOT_FOUND и возвращает ошибку в интерфейс: "Пользователь с таким номером телефона не найден".
* Сценарий 2: Недостаточно средств на счете списания.
  - Система прерывает операцию, логирует статус FAILED с кодом INSUFFICIENT_FUNDS и возвращает ошибку в интерфейс: "Недостаточно средств для совершения перевода".
* Сценарий 3: Превышен лимит на перевод (разовый или месячный).
  - Система прерывает операцию, логирует статус FAILED с кодом LIMIT_EXCEEDED и возвращает ошибку в интерфейс: "Превышен лимит на проведение операции "Лимит"".

Раздел 4. Структура базы данных 
Для обеспечения работы сервиса и хранения данных спроектированы 3 основные таблицы в реляционной СУБД (PostgreSQL / Pangolin).

4.1. Таблица users
Хранит персональные данные пользователей для их идентификации.
```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    phone_number VARCHAR(12) UNIQUE NOT NULL, -- Номер телефона клиента для поиска получателя
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL
);
```

4.2. Таблица accounts
Хранит информацию о счетах клиентов и их балансах. У одного пользователя может быть несколько счетов.
```sql
CREATE TABLE accounts (
    id SERIAL PRIMARY KEY,
    user_id INT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    account_number VARCHAR(20) UNIQUE NOT NULL,
    balance DECIMAL(15, 2) NOT NULL DEFAULT 0.00, -- Использование типа DECIMAL обязательно для предотвращения ошибок округления денежных средств
    currency VARCHAR(3) NOT NULL,                 -- Буквенный код валюты счета (например, RUB)
    status VARCHAR(20) NOT NULL DEFAULT "ACTIVE"  -- Статус счета для валидации ФТ-3 (ACTIVE, BLOCKED)
);
```

4.3. Таблица transactions
Логирует все транзакции между счетами клиентов.
```sql
CREATE TABLE transactions (
    id SERIAL PRIMARY KEY,
    sender_account_id INT NOT NULL REFERENCES accounts(id),
    recipient_account_id INT NOT NULL REFERENCES accounts(id),
    amount DECIMAL(15, 2) NOT NULL,
    status VARCHAR(20) NOT NULL,                  -- Статус платежа (PENDING, COMPLETED, FAILED)
    error_code VARCHAR(50) NULL,                  -- Код ошибки для анализа надежности системы при статусе FAILED
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```
